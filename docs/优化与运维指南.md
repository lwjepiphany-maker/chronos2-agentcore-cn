# 上线后怎么用、怎么调优、怎么换模型

面向日常使用者与运维人员。部署步骤见 README，数据格式见《销售数据格式说明》。

---

## 一、日常使用：三条路径

| 路径 | 什么时候用 | 用什么 |
|---|---|---|
| 数据刷新 | 每天把昨日销量追加进来 | 定时跑 `tools/export_from_db.py`，从数据库导出写入 `s3://<数据桶>/data/sales_daily.parquet`。Agent 按文件 ETag 检测变化，30 秒内自动切到新数据。前端上传 Excel 只是手工兜底 |
| 批量预测 | 每周（或每天）给所有门店出一张补货表 | 定时跑 `tools/batch_forecast.py`，直接读 S3 上的数据、直连预测服务，Excel 落到 `s3://<数据桶>/reports/`。也可以在前端对 Agent 说"所有门店 Top10 批量预测生成报表" |
| 临时问答 | 店长 / 运营随手问某个商品、促销场景、画图 | 前端对话（Streamlit） |

### 1.1 数据库定时导出

脚本只认两样东西：环境变量 `DB_URL`（怎么连库）和 `--sql` 指向的 SQL 文件（查什么）。**表名写在 SQL 里**，输出列名必须用中文标准列名，和 Excel 完全一致。

示例 `sql/daily_sales.sql`（按贵司表结构改写）：

```sql
-- 必需 4 列：记账日期、门店代码、商品代码、销售数量；其余列有就带上，对预测有帮助
SELECT sale_date        AS 记账日期,
       store_id         AS 门店代码,
       sku_code         AS 商品代码,
       SUM(qty)         AS 销售数量,
       MAX(sale_price)  AS 门店售价,
       MAX(promo_type)  AS 促销类型,
       SUM(promo_qty)   AS 促销数量,
       SUM(discount)    AS 优惠金额
FROM   t_sales_daily                 -- 换成贵司的表名
WHERE  sale_date >= :start_date      -- 脚本按 --days 自动填入
GROUP  BY sale_date, store_id, sku_code
```

在能访问数据库的机器上执行（首次需安装依赖）：

```bash
pip install -i https://mirrors.aliyun.com/pypi/simple sqlalchemy pymysql pandas pyarrow boto3
# MySQL 用 pymysql；SQL Server 换 pymssql；PostgreSQL 换 psycopg2-binary
export DB_URL='mysql+pymysql://user:pass@db-host:3306/retail'
python tools/export_from_db.py --sql sql/daily_sales.sql --days 400 \
    --upload s3://<数据桶>/data/sales_daily.parquet
```

`--days 400` 把一整年历史都带上。放进 crontab 每天凌晨跑一次即可，例如 `30 2 * * *`。

### 1.2 批量预测定时任务

```bash
python tools/batch_forecast.py \
    --parquet s3://<数据桶>/data/sales_daily.parquet \
    --chronos-arn <ChronosRuntimeArn> --top 10 --days 7 \
    --upload s3://<数据桶>/reports/
```

参数：`--stores 1 5 8` 指定门店（默认全部），`--top` 每店取前几名，`--days` 预测天数，`--history-days` 用多长历史（默认 60）。报表里每个商品每天有两列：**预计销量**（P50，日常备货按它）和**最多备货量**（P90，怕缺货、不易过期的商品按它）。

两条命令串起来就是完整的日常流水线：先导出，再批量预测。批量预测脚本不经过 Agent，数据传上去立刻可用，不受 30 秒热加载的影响。

## 二、调优：每两周一轮，每轮三步

先说一个前提：**Chronos-2 是零样本预训练模型，本方案里没有"训练"这一步。** 调优不是调模型参数，而是喂更好的数据、问更对的问题、选更合适的口径。

### 第一步：量现状

在前端输入：

> 5号店热销Top10最近4周的预测准确率，对比带业务因素和不带的

Agent 会做滚动回测：只用更早的数据预测后面几周，和真实销量比较，给出 WAPE（加权绝对百分比误差）和准确率。两个数字，一个是只用历史销量的基线，一个是加上节假日、促销、价格、天气的因子版。这就是本轮的起点。在贵司 2025～2026 年数据上的参考值：基线 64.5%，因子版 76.3%。

### 第二步：每轮只改一样东西

改完回到第一步再量一次，看数字有没有变好。按投入产出排序：

| 轮次 | 改什么 | 怎么改 | 预期效果 |
|---|---|---|---|
| 1 | 历史长度 | 导出时 `--days 400`，把断开的数据段补成连续一年 | 提升最大，覆盖春节、暑期、双十一等周期 |
| 2 | 促销列 | SQL 里把促销类型、促销数量、优惠金额、售价带上 | 促销商品误差明显下降 |
| 3 | 未来促销计划 | 预测时告知"下周五到周日促销价"，和不告知对比 | 促销周不再低估 |
| 4 | 分位数口径 | 短保商品按预计销量（P50）备货；长保、怕缺货的按最多备货量（P90） | 缺货率与损耗率的平衡，比改模型见效快 |
| 5 | 真实主数据 | 用 `iac/prepare_master.py` 把保质期、到货周期、箱规、库存快照转换后上传 `master/` | 补货建议从"演示"变成"可用"（当前为模拟数据） |
| 6 | 聚合粒度 | 销量稀疏的长尾商品改按周预测再拆分，或只对 ABC 分类中的 A/B 类做单品预测 | 长尾商品不再被日粒度噪声误导 |
| 7 | Agent 措辞与默认值 | 改 `app_agent/agent.py` 的系统提示词（默认天数、默认口径、表述方式），换 `IMAGE_TAG` 重跑 `deploy.sh` | 回答更贴合门店使用习惯 |

### 第三步：记录

每轮把两个准确率数字记进一张表。三个月后就有一条曲线，知道哪项改动值钱、哪项没用。

### 什么时候才考虑微调模型

Chronos-2 支持在自有数据上微调，但需要 GPU、足够的数据量和另一笔预算。只有上面 7 轮做完、准确率仍然到顶时才值得做。前三个月不建议碰模型。

## 三、预测和实际差了，怎么看、怎么归因

**先说清边界：Agent 不会自动做这件事。** 它不记住自己上周预测过什么，不会主动报告"预测 100 实际卖了 130"。差距的发现和归因需要人来触发，工具能帮一部分。

### 3.1 找出差距

**方式一：回测复现。** 10 月 17 日的真实数据进来后，在前端问：

> 5号店 12070007 这周（10月11日到17日）预测准不准

Agent 只用 10 月 10 日之前的数据重新预测这 7 天，和真实销量逐日比较。Chronos-2 是确定性模型，同样输入给同样输出，复现结果就等于当时的预测，不需要事先保存。

**方式二：对报表。** 如果当时是批量预测出的 Excel，它还在 `reports/` 下，有每个商品每天的 P50 / P90。和新数据对一下就是真实偏差。目前没有工具自动做这个对齐，要么在 Excel 里对，要么让 Agent 现算。

### 3.2 归因能做到什么程度

回测时让 Agent"对比带业务因素和不带的"，两版误差之差，就是节假日、促销、价格、天气**合起来**解释了多少。

再往下拆到单个因素，Agent 能做的是查证据：那几天有没有促销记录、是不是节假日、天气是否异常、价格有没有变，然后把线索串起来回答，例如"10 月 12 日卖了平时的 2 倍，当天有促销价且是周末"。这是基于证据的推理，不是统计意义上的因素分解。

它做不到的：

- 数据里没有的因素它看不见。竞品开业、断货导致少卖、系统录错，这些不在销售表也不在天气里，Agent 只会说"无法解释"。
- 不会把误差反馈给模型。Chronos-2 不从错误中学习。它唯一的"适应"是：新一周的真实销量进入历史窗口，下一次预测的上下文就包含这段新水平，预测会自然跟上。

### 3.3 下一阶段建议：预测 vs 实际工具

上线后这个问题每周都会问，现在靠人拼。建议下一阶段加一个 `forecast_vs_actual` 工具：读 `reports/` 里指定日期的报表，和新数据按门店、商品、日期对齐，输出逐日偏差，自动标注每天是否促销、节假日、天气异常、价格变动。Agent 拿到这张表再解释，归因就有据可依；每周准确率也能自动记录成曲线，替代第二节第三步的手工记录。改动不大，可和调优第一轮一起做。

## 四、换大模型、换 API Key

Agent 的大模型通过三个参数配置：`LLM_BASE_URL`（接口地址）、`LLM_MODEL`（模型名）、`LLM_API_KEY`（密钥，存在 AgentCore Identity 中，不出现在任何配置文件和日志里）。

### 4.1 对大模型的要求

- OpenAI 兼容的 Chat Completions 接口（`/v1/chat/completions`）
- 支持工具调用（function calling），否则 Agent 无法调用预测、回测、补货等工具
- 建议上下文 ≥ 32K，一次批量预测的工具返回可能较长

国内常用服务商（接口地址和模型名以服务商当前文档为准）：

| 服务商 | `LLM_BASE_URL` | `LLM_MODEL` 示例 |
|---|---|---|
| DeepSeek 官方 | `https://api.deepseek.com/v1` | `deepseek-chat` |
| PPIO | `https://api.ppinfra.com/v3/openai` | `deepseek/deepseek-v4-flash-0731` |
| 阿里云百炼（通义） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` / `qwen-max` |
| 火山引擎方舟（豆包） | `https://ark.cn-beijing.volces.com/api/v3` | 控制台里的接入点或模型名 |
| 智谱 | `https://open.bigmodel.cn/api/paas/v4` | `glm-4.5` |
| Moonshot（Kimi） | `https://api.moonshot.cn/v1` | 以控制台为准 |

换服务商前，建议先用新 Key 调一次接口确认可用：

```bash
curl -s https://api.deepseek.com/v1/chat/completions \
  -H "Authorization: Bearer $LLM_API_KEY" -H "Content-Type: application/json" \
  -d '{"model":"deepseek-chat","messages":[{"role":"user","content":"你好"}]}'
```

### 4.2 操作步骤

都是重跑部署脚本，参数不同。第 2 个参数传 `-` 表示不重新上传销售数据（否则会用本地旧文件覆盖 S3 上更新的数据）。

**情况 A：只换模型名或接口地址，Key 不变。** 约 2 分钟，不重建镜像：

```bash
LLM_API_KEY='<现有Key>' LLM_BASE_URL='https://dashscope.aliyuncs.com/compatible-mode/v1' LLM_MODEL='qwen-plus' \
bash iac/deploy.sh s3://<源码桶>/src.zip -
```

**情况 B：换 Key（含换服务商）。** 约 3 分钟。部署脚本会算一个 Key 指纹传给模板，指纹变化时跑一次很短的 CodeBuild 把新 Key 写进 Identity，镜像不重建：

```bash
LLM_API_KEY='<新Key>' LLM_BASE_URL='https://api.deepseek.com/v1' LLM_MODEL='deepseek-chat' \
bash iac/deploy.sh s3://<源码桶>/src.zip -
```

换 Key 后，前端里正在进行的会话仍用旧 Key，点“新会话”或刷新页面即用新 Key。

两种情况下脚本都会先用这把 Key 调一次接口做预检，模型名或 Key 不对会在部署前就报出来，并打印接口返回的原文（里面通常写明支持的模型名）。

**验证**：前端侧栏"大模型"一栏会显示新的模型名和接口；或执行

```bash
python tests/agent_cloud_test2.py <AgentRuntimeArn>
```

三轮对话都返回即正常。两个 Runtime 保留历史版本，如需回退，用旧参数重跑一次即可。

### 4.3 注意事项

- 对话内容（包括销售数字）会发送给大模型服务商，换服务商前请确认数据合规要求。
- 不同模型调用工具的风格不同，换模型后建议把第二节第一步的回测问题和常用问法各跑一遍，确认回答格式仍符合预期；必要时微调系统提示词（第二节第 7 轮）。
- Key 余额用尽时 Agent 会报"调用失败"，前端能看到具体错误；预测服务本身不依赖大模型，批量预测脚本不受影响。

## 五、其他运维操作速查

| 操作 | 命令 |
|---|---|
| 升级代码（改了 `app/` 或 `app_agent/`） | 重新打 zip 上传 S3，`IMAGE_TAG=v2 bash iac/deploy.sh s3://<源码桶>/src.zip -`，只重建改动过的镜像 |
| 排查报错 | 见 `docs/排障指南.md`：现象 → 原因 → 处理，附取日志命令 |
| 更新销售数据 | 定时导出（1.1）；或前端侧栏上传 Excel；或 `aws s3 cp xxx.parquet s3://<数据桶>/data/sales_daily.parquet` |
| 回退数据 | 数据桶开了版本控制，在 S3 控制台选旧版本恢复即可 |
| 更新主数据 / 库存 | `python iac/prepare_master.py` 转换后上传到 `s3://<数据桶>/master/` |
| 查调用链 | 前端"调用详情"里的 CloudWatch 链接，或 CloudWatch → Transaction Search 按 `service.name=chronos2_agent` 筛选 |
| 查费用 | Cost Explorer 按服务筛选 Bedrock AgentCore；大模型费用在服务商控制台 |
| 删除整套 | `aws cloudformation delete-stack --stack-name chronos2-agentcore`。数据桶与 ECR 镜像仓库保留（重新部署可秒级复用镜像），彻底清理需手动删桶和 `aws ecr delete-repository --force` |
