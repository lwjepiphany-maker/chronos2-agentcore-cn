# Chronos-2 销量预测：AgentCore Runtime（方案 B）宁夏区验证报告

> 验证日期：2026-10-08 · 区域：cn-northwest-1（宁夏） · 账号：<ACCOUNT_ID>（内部测试账号）
> 数据：每一天便利店 6 家门店真实销售数据（2025-03-01 ~ 2026-05-24，15,274 个门店-商品组合）

## 一、结论

**方案 B 在宁夏区可行**。Chronos-2 用 CPU 跑在 AgentCore Runtime 里，直接以 MCP Server 的形式提供服务，可以替换掉原来的"API Gateway + Lambda + SageMaker GPU 端点"三件套：

- 3 个工具（forecast / batch_forecast / forecast_with_covariates）的名称、参数和返回格式与原方案一致
- 预测结果与现有 GPU 端点 `chronos2-huimeijia` 一致（最大绝对误差 1.1e-4，属于浮点误差）
- 默认使用 IAM（SigV4）鉴权，匿名访问返回 403，不对公网开放
- 交互式场景的费用从"按小时付 GPU"变成"按会话付费"，POC 量级约 **¥25–60/月**（原方案约 ¥1,150–3,740/月）

```
业务人员 → AI 助手（Claude Code / Kiro / Cursor …）
          → mcp-proxy-for-aws（本地，用 AWS 凭证做 SigV4 签名）
          → AgentCore Runtime（MCP 协议 · microVM · 2 vCPU/8GB · Chronos-2 CPU 推理）
```

## 二、中国区与 Global 区的差异（只列本方案涉及的部分）

| 能力 | 中国区现状 | 对本方案的影响 |
|---|---|---|
| Runtime | 可用（仅 MicroVM） | ✅ 核心组件，已验证 |
| Runtime 入站鉴权 | IAM SigV4 可用；JWT 需用 **非 Cognito** 的 OIDC IdP（宁夏没有 Cognito） | 本次用 IAM 验证。没有 AWS 凭证的业务用户需要另接 OIDC IdP（未验证） |
| Gateway | 可用，但不支持 "No auth"、语义搜索、WAF | 本方案不需要 Gateway，客户端直接连 Runtime |
| Memory / Policy / Evaluations 等 | 不可用 | 本方案不依赖 |
| Bedrock 模型 | 不可用 | LLM 跑在客户端（Claude/Kiro 等），不受影响；如果要在云上托管 Agent，需要用 DeepSeek/Qwen/Kimi 等模型 |
| 依赖安装 | PyPI/HF 不稳定 | 镜像构建时用清华源，权重来自 ModelScope 并打进镜像，运行时不需要外网 |

## 三、测试结果

### 3.1 延迟（客户端在本地 Mac，经公网 HTTPS 到宁夏）

| 用例 | AgentCore（CPU，热会话） | SageMaker GPU 端点 | 与 GPU 的最大误差 |
|---|---|---|---|
| 单品 30 天历史 → 7 天（forecast） | 0.40–0.47 s | 1.16 s | 7.6e-06 |
| 单品 + 天气/温度/星期协变量（60 天） | 0.51 s（首次 2.3 s） | 0.78 s | 4.2e-05 |
| 批量 100 个 SKU | 3.0 s | 1.27 s | 8.0e-05 |
| 批量 1,000 个 SKU | 26 s（服务端 23 s） | 3.9 s | 1.1e-04 |

| 冷启动指标 | 结果 |
|---|---|
| 新会话 initialize + tools/list | 3.1–4.6 s（经 stdio 代理 5.9 s） |
| 新会话的首次推理 | v1：27–35 s → v2 加入启动预热后：**< 0.5 s** |
| 部署/更新 Runtime 到 READY | 约 4 分钟 |

结论：单品/协变量这类交互式查询，CPU 的端到端延迟和 GPU 相当甚至更低（瓶颈在网络，不在算力）；大批量时 CPU 明显慢于 GPU（1,000 条约 6.7 倍），但每日全量跑批仍然可以接受（见 3.3）。

### 3.2 精度（用最后 7 天真实销量回测，p50 的 WAPE）

| 用例 | WAPE |
|---|---|
| 单品 30 天 | 0.38 |
| 单品 + 协变量 60 天 | 0.42 |
| Top 100 组合 | 0.29（约 71% 精度，与原方案报告的"约 70%"一致） |
| Top 1000 组合 | 0.48 |

数值与 GPU 端点一致，所以精度和原方案相同。

### 3.3 实测资源用量（CloudWatch `AWS/Bedrock-AgentCore`）

| 状态 | vCPU（实际消耗） | 内存（计费口径） |
|---|---|---|
| 单个会话空闲等待 | ≈ 0.03 vCPU | ≈ 1.4–1.5 GB |
| 批量推理 1,000 条期间 | ≈ 1.3–2 vCPU | 峰值约 3–5 GB |

**结构化对比**：

| 维度 | 原方案（APIGW + Lambda + GPU） | 方案 B（AgentCore Runtime） |
|---|---|---|
| 月成本（POC） | ¥1,150–3,740 | ¥25–60 |

**推荐**：交互式查询 + 每日跑批这种负载（万级 SKU），**建议采用方案 B**，成本可降低 95% 以上，鉴权也更安全。只有当跑批规模达到十万级 SKU 以上、并且对时效要求很高时，才考虑保留 GPU 端点（或改用 SageMaker Batch Transform）专门负责跑批。

## 五、本次发现并已修复的两个问题（迁移时必须保留）

| 问题 | 现象 | 修复 |
|---|---|---|
| SSE 流式响应 + 慢请求导致客户端卡住 | 标准 MCP 客户端（mcp-proxy-for-aws）在耗时较长的第一次调用上一直挂起 | `FastMCP(..., stateless_http=True, json_response=True)`，改为返回普通 JSON |
| 新 microVM 的首次推理很慢 | 首次调用 27–35 s（镜像层按需加载，第一次才读 480MB 权重） | 启动时在后台线程预读权重并做一次推理（`_warmup()`），端口立即可用 |

## 六、风险与注意事项

1. **客户端需要 AWS 凭证**：IAM 方式要求每个用户有 `bedrock-agentcore:InvokeAgentRuntime` 权限，并在本地运行 `mcp-proxy-for-aws`。如果业务人员没有 AWS 账号，需要接入客户已有的 OIDC IdP（宁夏没有 Cognito），这部分**尚未验证**。
2. **单会话资源上限是 2 vCPU / 8GB**：大批量请求建议按 1,000 条一批拆分，或者开多个会话并行。
3. **空闲超时要权衡**：设得短更省钱，但下一次使用要冷启动（3–5 s）。POC 建议设 300–900 s。
4. **镜像推送**：镜像 804MB，从本地推到宁夏 ECR 约 13 分钟。生产环境建议在区域内构建（CodeBuild/EC2）。
5. **客户端配置**：mcp-proxy-for-aws 需要显式指定 `--service bedrock-agentcore --region cn-northwest-1`（`.amazonaws.com.cn` 域名可能推断不出来）。

## 七、客户端接入示例（Claude Code）

```bash
RUNTIME_ARN='arn:aws-cn:bedrock-agentcore:cn-northwest-1:<ACCOUNT_ID>:runtime/<RUNTIME_ID>'
URL="https://bedrock-agentcore.cn-northwest-1.amazonaws.com.cn/runtimes/$(python3 -c "import urllib.parse,sys;print(urllib.parse.quote(sys.argv[1],safe=''))" "${RUNTIME_ARN}")/invocations?qualifier=DEFAULT"
claude mcp add --scope user chronos2-agentcore -- \
  uvx mcp-proxy-for-aws@latest "${URL}" --service bedrock-agentcore --region cn-northwest-1
```

（已通过 Python MCP SDK 以 stdio 方式启动 mcp-proxy-for-aws v1.7.0 验证，链路一致。）
