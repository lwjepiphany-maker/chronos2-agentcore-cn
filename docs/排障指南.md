# 部署与运行排障指南

按"现象 → 原因 → 处理"整理，全部来自真实部署现场。先看第一节的通用取证命令，再按现象查表。

---

## 一、先取证：三条命令

**1. CloudFormation 失败在哪一步**

```bash
aws cloudformation describe-stack-events --stack-name chronos2-agentcore --region cn-northwest-1 \
  --query "StackEvents[?ResourceStatus=='CREATE_FAILED' || ResourceStatus=='UPDATE_FAILED'].[LogicalResourceId,ResourceStatusReason]" --output table
```

**2. 镜像构建（CodeBuild）日志**。栈事件里 `ImageBuild` 失败时会给出构建 ID：

```bash
# 列出最近的构建
aws codebuild list-builds-for-project --project-name chronos2-agentcore-image-build --region cn-northwest-1 --max-items 3
# 导出整份日志（把 <build-id> 换成 chronos2-agentcore-image-build:xxxxxxxx-...）
aws logs tail /aws/codebuild/chronos2-agentcore-image-build --since 2h --region cn-northwest-1 --format short > build.log
# 只看关键行
grep -nE '^==>|ERROR|WARNING|hash tag|Phase complete' build.log | grep -v echo | head -60
```

日志里每个 `==>` 是一个阶段：fetch source → model weights → build & push images → LLM API key → Transaction Search。看最后一个 `==>` 后面的 ERROR 就是失败点。

**3. Agent 运行日志**（前端报"调用失败"时）

```bash
AGENT_ID=$(aws cloudformation describe-stacks --stack-name chronos2-agentcore --region cn-northwest-1 \
  --query "Stacks[0].Outputs[?OutputKey=='AgentRuntimeArn'].OutputValue" --output text | awk -F/ '{print $NF}')
aws logs tail "/aws/bedrock-agentcore/runtimes/${AGENT_ID}-DEFAULT" --since 1h --region cn-northwest-1 --format short \
  | grep -iE 'exception|error' | grep -v 'File "' | tail -20
```

从当前版本起，Agent 内部异常会直接作为回答文本返回到前端（"调用失败：…"），一般不再需要翻日志。

## 二、部署阶段

| 现象 | 原因 | 处理 |
|---|---|---|
| 栈事件 `ImageBuild ... build failed`，构建日志 `git clone` 报 `SSL_read: unexpected eof` 或超时 | 客户账号的 CodeBuild 出不了网到 GitHub（常见于有出网管控的账号） | 在能访问 GitHub 的机器上把仓库打成 zip 放到客户 S3，`deploy.sh` 第一个参数改为 `s3://<桶>/src.zip`。打包命令：`zip -rq src.zip . -x '.git/*' 'data/*' '.venv/*' '*/__pycache__/*'` |
| 构建日志 pip 报 `Connection broken: InvalidChunkLength` 或 `THESE PACKAGES DO NOT MATCH THE HASHES`（Got `e3b0c442…`） | 某个国内 PyPI 镜像站抖动或返回空文件（`e3b0c442…` 是空文件的哈希） | 已内置：每次只用一个镜像站，阿里云 → 华为云 → 中科大 → 清华轮换。仍失败就等几分钟重跑 |
| 构建日志 `AccessDeniedException ... UpdateTraceSegmentDestination` / `logs:CreateLogGroup ... aws/spans` | 首次开启 CloudWatch Transaction Search 需要建日志组，角色权限不足 | 已修复（角色补权限，且该步改为尽力而为）。日志出现 `WARNING: could not enable CloudWatch Transaction Search` 时部署仍成功，只是看不到调用链，由账号管理员执行 `aws xray update-trace-segment-destination --destination CloudWatchLogs` 即可 |
| 构建 50 分钟超时 | 镜像站慢，torch（160 MB）+ 模型权重（478 MB）下载不完 | 等 CloudFormation 回滚后直接重跑同一命令。镜像按源码内容哈希复用，已经推上去的那个镜像不会重建 |
| `aws cloudformation deploy` 报栈处于 `ROLLBACK_COMPLETE` 不能更新 | 首次创建失败后的栈不能原地更新 | `aws cloudformation delete-stack --stack-name chronos2-agentcore` 并 `wait stack-delete-complete`，再 `aws s3 rb s3://chronos2-agent-data-<账号>`（空桶），然后重跑。**镜像保留在 ECR，不会重建** |
| 重跑后镜像又从头构建了 | 旧版模板把 ECR 仓库放在栈里，删栈即删镜像 | 已修复：ECR 仓库由构建脚本创建、不随栈删除。完全清理需手动 `aws ecr delete-repository --force --repository-name chronos2-forecast`（及 `chronos2-agent`） |
| 删栈后重新部署报数据桶已存在（`chronos2-agent-data-<账号> already exists`） | 数据桶设为删栈保留（防误删数据），但重建栈会尝试再建同名桶 | 先把桶里的数据备份下来（`aws s3 sync s3://<桶> ./backup`），清空并删桶后重跑；或改 `PREFIX` 用新名字部署，再把数据拷过去 |
| Windows 上 `aws cloudformation deploy` 报 `gbk` 编码错误 | 模板含中文，Windows 默认 GBK | `$env:AWS_CLI_FILE_ENCODING="UTF-8"; $env:PYTHONUTF8="1"` 后重跑 |
| `deploy.sh` 第 0 步"预检大模型接口"失败 | 模型名 / 接口地址 / Key 任一不对，或余额不足 | 看打印出的接口返回，`message` 里通常写明支持的模型名。改对再跑；确认无误仍要继续可加 `SKIP_LLM_CHECK=1` |

## 三、运行阶段

| 现象 | 原因 | 处理 |
|---|---|---|
| 前端"调用失败：BadRequestError … The supported API model names are …" | `LLM_MODEL` 写了接口不认的模型名 | 用接口返回里列出的名字，重跑 `deploy.sh`（第 2 个参数传 `-`），约 2 分钟，不重建镜像 |
| "调用失败：AuthenticationError / 401" | Key 不对，或 Key 与接口地址不配套（例如 PPIO 的 Key 配了 DeepSeek 官方地址） | 核对后重跑 `deploy.sh`，Key 变化会自动写入 Identity（约 3 分钟） |
| "调用失败：… 402 / Insufficient Balance" | 大模型账户余额不足 | 充值；预测服务和批量预测脚本不依赖大模型，不受影响 |
| "销售数据未就位" | `s3://<数据桶>/data/sales_daily.parquet` 不存在 | 前端侧栏上传 Excel，或 `aws s3 cp xxx.parquet s3://<数据桶>/data/sales_daily.parquet` |
| 旧版本（无错误直返）前端只显示 `Received error (500) from runtime` | Agent 内部异常被包装成 500 | 用第一节第 3 条命令取日志，`exception.message` 是原因；升级到当前版本后前端直接显示原因 |
| 第一次提问 10～20 秒才回 | 新版本容器冷启动 + 连接预测服务 | 正常，后续提问 3～8 秒 |
| 前端侧栏"大模型"显示的还是旧模型名 | 浏览器缓存了 10 分钟 | 刷新页面，或等待 |
| 调用链"拉取瀑布图"提示还在上报 | X-Ray 数据通常延迟 30～90 秒 | 稍后再点；若始终没有，检查 Transaction Search 是否开启（见第二节） |

## 四、升级 2026-10-28 之前部署的旧栈（必读）

当前模板把 ECR 仓库移出了栈。**直接用新模板更新旧栈，CloudFormation 会把两个 ECR 仓库连同镜像一起删掉**，运行中的 Runtime 随后拉不到镜像。升级分两步，都在仓库目录执行，参数和平时部署一致：

```bash
# 第 1 步：中间模板（= 旧模板 + ECR 仓库 Retain），约 1 分钟，让 CloudFormation 记住"删除时保留仓库"
aws cloudformation deploy --stack-name chronos2-agentcore --template-file iac/migrate/step1-retain-ecr.yaml \
  --capabilities CAPABILITY_NAMED_IAM --no-fail-on-empty-changeset --region cn-northwest-1 \
  --parameter-overrides SourceS3Uri=s3://<源码桶>/src.zip LlmApiKey='<Key>' LlmBaseUrl='<接口>' LlmModel='<模型>'

# 第 2 步：正常重跑部署脚本（新模板）。镜像保留，只跑一次约 2 分钟的 config 构建
LLM_API_KEY='<Key>' LLM_BASE_URL='<接口>' LLM_MODEL='<模型>' bash iac/deploy.sh s3://<源码桶>/src.zip -
```

第 2 步结束后 ECR 仓库不再属于栈，但镜像原样保留，Runtime 不受影响。要同时拿到新的 Agent 代码（错误直返等），第 2 步加 `IMAGE_TAG=v2`，Agent 镜像会重建（约 15 分钟），预测服务镜像复用。

怎么判断栈是不是旧版：`aws cloudformation describe-stack-resources --stack-name chronos2-agentcore --query "StackResources[?ResourceType=='AWS::ECR::Repository'].LogicalResourceId"` 有输出就是旧版。

## 五、为什么我们自己账号测试没问题，到客户账号才出错

四个真实案例，供以后部署前对照：

- **出网环境不同**：客户 CodeBuild 连不上 GitHub。现在默认建议走 S3 zip 源。
- **账号级状态掩盖了权限缺口**：我们账号早就开过 Transaction Search，日志组已存在，角色少一个 `logs:CreateLogGroup` 不会暴露。验证应在从未开启过该功能的账号里做。
- **外部依赖当时的健康状态**：镜像站当天故障。设计上不能让任一外部站点单点失败。
- **"删栈后镜像复用"是推断不是实测**：只验证过回滚场景，没验证过删栈重建。现在 ECR 已脱离栈生命周期，并实际验证过删栈再部署。
